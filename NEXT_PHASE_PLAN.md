## Executive Summary

FitStudio Pro has already shipped far more than a typical MVP: all core backend modules are
built and unit-tested (168+ tests), a full owner/trainer dashboard exists, a BullMQ reminder
worker runs end-to-end, and — in the current working tree — a complete platform-admin console
has just been added. Despite this volume of work, the product is not yet feature-complete or
sellable: the **Client** role (one of three core personas in the brief) has no usable portal,
email/AI features are fully stubbed, there is no file storage, no real payment processing
(for studios *or* for FitStudio Pro itself), no group-class scheduling, no public marketing
presence, and no CI/CD or deployment pipeline. This plan defines **11 phases**, strictly
ordered by dependency, that take the product from "impressive demo" to "a studio owner can
discover it, pay for it, run their business in it, and their clients can use it on day one."
Phases 1–2 close foundational/dev-velocity gaps and finally make the **client** role real;
Phases 3–4 complete the communication/AI/media features deferred mid-MVP; **Phases 5a–5b
introduce real money movement** — the single biggest unlock for "sellable," and the most
significant new complexity in this plan; Phases 6–9 round out scheduling, analytics, public
presence, and UI polish to match Mindbody/Glofox/TeamUp; Phase 10 ships it to production with
monitoring. "Done" means: a logged-out visitor finds pricing and signs up, a new studio owner
onboards and starts charging real clients on a paid FitStudio Pro plan, every role
(owner/trainer/client/admin) has a working dedicated experience, and the stack is deployed,
monitored, and covered by CI.

> **Note on scope**: this plan picks up *after* the existing Phase 0–9 (+8.5) work tracked in
> `fitstudio-pro-mvp-mvc-scalable-plan.md` (see that document's "Scale Roadmap After MVP"
> section, now superseded by this one). Phase numbering below restarts at 1.
>
> **Flagged assumption**: the original project brief listed "real payments / Stripe billing"
> under "Skip for Version 1." This plan deliberately brings real Stripe billing back into
> scope (Phases 5a/5b) because it is the single biggest lever for "sellable" — the framing this
> plan was commissioned under. This is the most consequential scope decision here; if you'd
> rather defer real payment processing, Phases 5a/5b can be moved to Deferred and the rest of
> the roadmap (6–10) is unaffected except that Phase 7's revenue analytics and Phase 8's
> pricing page would need to degrade gracefully (both already designed to do so).

## Product Gap Analysis

### Core Features
- **No client self-service portal** — `dashboard-shell.tsx`'s nav is entirely
  owner/trainer-oriented with no branching on `activeRole`; clients (a defined first-class
  role) can't see their own workouts/sessions/check-ins/progress. → **Phase 2**
- **Notifications backend has no frontend** — the queue → worker → `notifications` table → REST
  pipeline is fully wired, but there is zero bell/dropdown/page consuming it, so reminders are
  invisible to users. → **Phase 2**
- **Email delivery and AI weekly summaries are fully stubbed** — `EMAIL_API_KEY`/`AI_API_KEY`
  env vars and the `ai_summaries`/`emails`/`weekly-summaries` queues exist, but nothing
  produces or consumes jobs on them. Two "headline" features from the brief are non-functional.
  → **Phase 3**
- **No Supabase Storage buckets exist** — `avatar_url` and progress photos are dead DB columns
  with no upload path, despite being core to the brief's vision. → **Phase 4**
- **Forgot/reset-password** — ✅ **FIXED** (June 25, 2026). Frontend implementation was correct; issue was Supabase redirect URL config with invalid `**` wildcards. Fixed in `supabase/config.toml` line 158. See `PASSWORD_RESET_FIX_SUMMARY.md`. → **Phase 2 COMPLETE**
- **Only 1:1 trainer↔client sessions exist** — there is no group/class scheduling with
  capacity/waitlist, which is the core value proposition of Mindbody/Glofox/TeamUp.
  → **Phase 6**

### Architecture
- **Duplicated type definitions** — `frontend/lib/types.ts` (152 lines, hand-written) manually
  mirrors `backend/src/types/database.types.ts` (Supabase-generated, ~30KB). This drift risk
  compounds with every new table this plan adds. → **Phase 1**
- **No API versioning** — `backend/src/app.ts` is a flat list of `app.use('/api/...')`
  registrations. Future clients (and this plan's own new modules) will accumulate
  breaking-change risk without a version boundary. → **Phase 1**
- **No rate limiting, error tracking, or caching layer** — zero production-readiness
  instrumentation exists anywhere in the stack. → **Phase 1** (rate limiting/Sentry),
  **Phase 7** (analytics caching, reusing the existing Redis singleton)
- **One redundant no-op migration** — `20260525101235_add_email_to_profiles.sql` duplicates an
  earlier migration's column-add. Minor schema hygiene debt. → **Sprint 0**

### UX Flows
- **No public landing/pricing page** — `frontend/app/page.tsx` immediately redirects to
  `/dashboard`, so the product can't be discovered or sold to a prospective studio owner.
  → **Phase 8**
- **No studio-owner onboarding flow** — new owners land on a bare "create studio" card with no
  guidance toward inviting trainers or picking a plan. → **Phase 8**
- **The new admin module has zero automated tests** — despite covering high-blast-radius
  actions (role escalation, password resets, studio deletion). → **Sprint 0 / Phase 1**
- **Inconsistent UI primitives** — only 5 shadcn components exist (button/card/dialog/
  input/label); admin and dashboard pages hand-roll tables/selects/badges inconsistently, and
  every later phase will add more ad-hoc versions if this isn't consolidated. → **Phase 9**

### Revenue Blockers
- **`payments`/`subscription_plans`/`client_subscriptions` are pure schema** — zero
  payment-processor integration exists, so studios cannot actually charge their members.
  → **Phase 5a**
- **FitStudio Pro itself has no mechanism to charge studio owners** — the SaaS has no revenue
  model implemented at all. → **Phase 5b**
- **No plan-tiering / feature gating exists** — even once billing exists, there's no way to
  differentiate free vs. paid studios. → **Phase 5b**

### DX/Infra
- **No CI pipeline** — `.github/workflows` doesn't exist, despite the root `package.json`
  already having working `lint`/`typecheck`/`test`/`build` scripts across all 3 workspaces that
  a workflow could run as-is. → **Sprint 0 / Phase 1**
- **No deployment configuration anywhere** — no Dockerfile, no `render.yaml`, no Vercel config.
  The product has never been deployed. → **Phase 10**
- **Zero frontend tests and zero worker tests** — despite `jest`/`ts-jest` already being
  configured in `worker/package.json`. → **Phase 1** (worker), **Phase 9** (frontend)
- **`supabase/seed.sql` seeds only the exercise library** — there is no demo
  studio/owner/trainer/clients for sales demos or onboarding QA. → **Sprint 0**

## Detailed Phase Breakdown

### Phase 1 — Foundation Hardening & Dev Velocity

**Goal:** Eliminate the test/CI/type-safety gaps that would otherwise compound across 10 more
phases of new modules and tables.

**Unlocks:** every later phase can rely on CI catching regressions, a single source of truth
for DB types, and a versioned API boundary.

**Features & Tasks:**
- **GitHub Actions CI** (`.github/workflows/ci.yml`) running `npm ci && npm run lint && npm run
  typecheck && npm run test && npm run build` via the existing root `--workspaces` scripts.
  *Rationale:* zero CI exists today; this is pure wiring of already-working scripts and is the
  cheapest possible regression safety net before 10 phases of new code land.
- **Shared-types via TS path mapping** — add
  `"@shared/database": ["../backend/src/types/database.types.ts"]` to `frontend/tsconfig.json`
  paths, and progressively replace hand-written interfaces in `frontend/lib/types.ts`.
  *Rationale:* removes the manual-sync drift risk before Phases 4–6 add new tables that the
  frontend will need to consume.
- **Admin module tests** (`backend/src/modules/admin/*.test.ts`) covering `adminMiddleware`
  rejection of non-admins, `getSystemStats`, `updateUserRole`, `resetUserPassword`,
  `deleteStudio`. *Rationale:* the highest blast-radius module in the codebase currently has
  zero automated coverage.
- **Worker tests** (`worker/src/worker.test.ts`) covering the reminder-scan
  pending→sent/failed paths and client/trainer notification branches, mocking
  `supabaseAdmin`. *Rationale:* the worker is load-bearing for Phase 3's email queue and has no
  regression protection today.
- **API versioning** — wrap all `app.use('/api/...')` registrations in `backend/src/app.ts`
  into a `v1Router` mounted at both `/api/v1` (canonical) and `/api` (temporary alias).
  *Rationale:* mechanical, non-breaking change now; every new module from Phase 2 onward
  mounts directly under `/api/v1` instead of accumulating un-versioned routes.
- **Sentry + rate limiting** (`express-rate-limit`/`rate-limit-redis`, reusing
  `backend/src/lib/redis.ts`'s `getRedisClient()`) on `/api/auth/*` and `/api/admin/*`.
  *Rationale:* zero error visibility and no brute-force protection currently exist on the two
  most security-sensitive route groups.

**Technical Notes:**
- Check `backend/jest.config.cjs` first: existing tests mock `supabaseAdmin`, so CI likely
  needs no live-DB service container — a single Node 20 job suffices.
- Use `import type` only for the shared-types path mapping — erased at compile time, no
  runtime cross-workspace coupling.
- New dependencies: `@sentry/node`, `express-rate-limit`, `rate-limit-redis`.

**Definition of Done:**
- [ ] `.github/workflows/ci.yml` runs on PR and passes on `main`.
- [ ] `backend/src/modules/admin/*.test.ts` cover happy path + auth/role-check failures for
      every admin endpoint.
- [ ] `worker/src/worker.test.ts` covers pending→sent and pending→failed paths.
- [ ] All existing `/api/*` routes respond identically under `/api/v1/*`.
- [ ] A deliberately-thrown test error appears in Sentry within minutes.

**Risks & Mitigations:**
- *Admin module is large (7 sub-resources) — test-writing could balloon* → prioritize
  authorization tests first, reuse `clients`/`sessions` test files as mocking templates.
- *Adding CI retroactively may surface long-standing lint/type issues* → fix forward in small
  PRs before enabling required-status-check branch protection.
- *Shared-types path mapping could create awkward build coupling if misused for runtime
  imports* → enforce `import type` via a lint rule.

### Phase 2 — Member Experience & Client Portal

**Goal:** Turn "Client" from a database role into a real, usable product experience.

**Unlocks:** the product now serves all three personas defined in the brief, not just two —
prerequisite for any client-facing feature in later phases (self-booking in Phase 6, progress
photos in Phase 4, AI summaries in Phase 3).

**Features & Tasks:**
- **Auto-create a Supabase Auth user** when a trainer creates a client with no matching
  existing profile (per `futureModifications.md` item 1). *Rationale:* today
  `clients.user_id` stays `null` forever in the common case, so most clients never get a portal
  account at all — this is the root blocker for the entire client-portal concept.
- **`POST /api/auth/change-password` + forced password-change screen.** *Rationale:*
  auto-created accounts share a default password (`fitstudio@123@`); without forcing a change
  on first login this is a credential-sharing hole.
- **Role-based dashboard nav** — branch `dashboard-shell.tsx`'s `NAV_ITEMS` on
  `activeRole === 'client'` (already computed in `studio-context.tsx`) to show "My
  Workouts/Sessions/Check-ins/Progress" instead of the owner/trainer management nav.
  *Rationale:* this is the actual "portal" — without it, clients log into an interface built
  for trainers.
- **Client-facing pages** reusing existing client-scoped, RLS-backed endpoints. *Rationale:*
  mostly view composition, not new backend logic — the data access is already
  correctly-scoped.
- **Notifications bell/dropdown** using the already-installed
  `@radix-ui/react-dropdown-menu`, calling `GET /api/notifications` +
  `PATCH /api/notifications/:id/read`. *Rationale:* the backend has been ready since Phase 8.5
  — this is the cheapest high-visibility win in the whole roadmap.
- **Unblock forgot/reset-password** per `memory/project_forgot_password_fix.md`. *Rationale:*
  code is already correct; only local Supabase Auth Site URL/Redirect URL configuration is
  blocking, and this becomes load-bearing once clients have real accounts they need to recover.

**Technical Notes:**
- New `backend/src/modules/auth/auth.schema.ts` (doesn't exist yet) with
  `changePasswordSchema` (zod, `newPassword.min(8)`); `changePassword()` in `auth.service.ts`
  calls `supabaseAdmin.auth.admin.updateUserById(userId, { password, user_metadata: {
  ...existing, must_change_password: false } })`.
- `getMe` must surface `mustChangePassword: req.user.user_metadata?.must_change_password ??
  false` — no extra DB call, `req.user` already comes from `auth.middleware.ts`.
- `clients.service.ts` `createClient`: when `findProfileByEmail` finds no match and an email
  was provided, call `supabaseAdmin.auth.admin.createUser({ email, password:
  'fitstudio@123@', email_confirm: true, user_metadata: { full_name, must_change_password:
  true } })`; the existing `handle_new_user` trigger creates the `profiles` row. Wrap in
  try/catch (warn-and-continue, same pattern as `enqueueSessionReminders`) so failures don't
  block client creation; keep `linkClientProfile` as the fallback for pre-existing
  null-`user_id` clients.
- New `frontend/components/notifications-dropdown.tsx`, polled on an interval (no
  WebSocket/SSE infra — explicitly deferred).

**Definition of Done:**
- [ ] Creating a client with an email matching no profile results in a real `auth.users` row
      and `clients.user_id` populated (new test case in `clients.service.test.ts`).
- [ ] `POST /api/auth/change-password` updates the password and clears `must_change_password`.
- [ ] A `studio_members.role === 'client'` user sees a distinct nav and cannot reach
      Clients/Settings/studio-wide Analytics.
- [ ] Notifications bell shows unread count and marks-as-read end-to-end against
      worker-populated `notifications`.
- [ ] Forgot/reset-password works end-to-end against local Supabase (verified via Mailpit);
      `memory/project_forgot_password_fix.md` updated to resolved.

**Risks & Mitigations:**
- *Auto-creating accounts for every client could create account-management noise* (already an
  open question in `futureModifications.md`) → ship as decided ("auto-create immediately"),
  revisit only if it becomes a real operational problem.
- *`createUser` calls add new latency/failure modes to `createClient`* → warn-and-continue,
  leave `user_id` null on failure for manual `linkClientProfile` follow-up.
- *Role-nav branching could regress existing nav if `activeRole` is transiently null* →
  default to the current owner/trainer nav unless `activeRole === 'client'` is explicitly
  true.

### Phase 3 — Communication & AI Layer

**Goal:** Make the two "headline" brief features (reminder emails, AI weekly summaries)
actually work — they're fully scaffolded but inert.

**Unlocks:** real email deliverability becomes available for every later phase that needs it
(Phase 5's payment receipts, Phase 8's invite emails); AI summaries become a demo/marketing
differentiator.

**Features & Tasks:**
- **Pick and integrate an email provider — Resend.** *Rationale:* env vars
  `EMAIL_API_KEY`/`EMAIL_FROM` and the `emails` queue name already exist in
  `backend/src/lib/queues.ts`; nothing produces or consumes jobs on it yet.
- **Wire an `emails` queue producer** for session reminders (extends the existing
  `enqueueSessionReminders` pattern in `sessions.service.ts`), portal invites, and password
  resets. *Rationale:* reuses an established, tested pattern rather than inventing a new one.
- **Add an `emails` queue consumer in `worker/`**
  (`worker/src/processors/email.processor.ts`) — refactor `worker/src/worker.ts`'s monolithic
  loop into one `Worker` per queue (`reminders`, `emails`, `weekly-summaries`) sharing
  `getRedisClient()`/`supabaseAdmin`, as its own structural-move commit (existing tests must
  still pass) before adding new logic. *Rationale:* keeps the working `reminders` queue
  protected while extending the worker's responsibilities.
- **Pick an AI provider — Anthropic Claude via `@anthropic-ai/sdk`.** *Rationale:* env vars are
  already generically named `AI_API_KEY`/`AI_MODEL` (not OpenAI-specific). At implementation
  time, use the `claude-api` skill to confirm the current recommended model id/pricing for a
  cost-effective per-client weekly summary rather than guessing.
- **Wire a `weekly-summaries` queue consumer** that reads the last 7 days of workout
  logs/check-ins/measurements/sessions for active clients and writes to `ai_summaries`,
  hardcoding the safety rules from the brief (no medical advice, no diagnosis, no outcome
  promises, trainer-focused) into the system prompt server-side. *Rationale:* this is a
  brief-mandated headline feature and the safety constraints are non-negotiable, so they belong
  server-side, not in a prompt a client could tamper with.
- **Surface the latest `ai_summaries` row** on the client detail page with a visible
  "AI-generated, not medical advice" disclaimer.

**Technical Notes:**
- New `backend/src/lib/email.ts` (Resend client singleton, mirrors the `lib/redis.ts`
  singleton pattern) — email is cross-cutting, called from `sessions`/`auth`/`clients`
  services, not its own module.
- New `backend/src/lib/ai.ts` (Anthropic client singleton).
- `EMAIL_API_KEY`/`AI_API_KEY` move from optional to required (for non-test environments) in
  `backend/src/config/env.ts`.

**Definition of Done:**
- [ ] Session-reminder emails received via local Mailpit (`http://localhost:54324`).
- [ ] `email.processor.test.ts` and `weekly-summary.processor.test.ts` pass.
- [ ] A scheduled run populates `ai_summaries` for active clients with check-in data from the
      last 7 days.
- [ ] Client detail page renders the latest summary with disclaimer.

**Risks & Mitigations:**
- *AI cost scales with client count × frequency* → use a cheap/fast model, skip clients with
  no new data in the period.
- *Email deliverability (spam) undermines a "sellable" product* → document Resend domain
  verification (SPF/DKIM) as a Phase 10 deployment prerequisite.
- *The worker refactor could regress the working `reminders` queue* → do the structural move
  first as its own commit with passing tests, then layer in new processors.

### Phase 4 — Storage & Media

**Goal:** Implement the file-upload features the brief specifies but were never built.

**Unlocks:** richer client profiles (avatars) and progress visualization (photos) — both
expected in any fitness SaaS and currently dead DB columns.

**Features & Tasks:**
- **Create Supabase Storage buckets** (`avatars`, `progress-photos`) via a new migration.
  *Rationale:* zero buckets exist today; `profiles.avatar_url` is a column nothing ever writes
  to.
- **Storage RLS policies** mirroring the existing security-definer helper pattern
  (`is_studio_member`, `is_studio_owner`) from `20260524094428_harden_rls_policies.sql`.
  *Rationale:* reuses an established, audited authorization pattern instead of inventing
  storage-specific rules from scratch.
- **Avatar upload UI** in studio settings — `dashboard-shell.tsx` already conditionally renders
  `avatar_url` (currently always null). *Rationale:* the UI slot already exists; this closes
  the loop.
- **Progress-photo upload on check-in** (trainer dashboard + Phase 2's client portal check-in
  view). *Rationale:* a core retention feature for fitness clients and explicitly part of the
  brief's vision.

**Technical Notes:**
- Path convention: `avatars/{user_id}/{filename}`,
  `progress-photos/{client_id}/{check_in_id}/{filename}` — encodes ownership in the path so
  RLS can use `storage.foldername(name)[1]`.
- Frontend uploads go directly via `@supabase/supabase-js` storage client (already a
  dependency) — no new backend upload endpoint; backend only needs a new nullable `photo_url`
  column on `check_ins` (one photo per check-in for v1, not a join table).
- Regenerate `database.types.ts` via `supabase gen types typescript` (already a workspace
  devDependency) — first real exercise of Phase 1's shared-types pipeline.

**Definition of Done:**
- [ ] `supabase db reset` creates `avatars`/`progress-photos` buckets with RLS blocking
      cross-user/cross-studio access.
- [ ] Settings page can upload/replace an avatar; `profiles.avatar_url` updates and renders.
- [ ] Check-in form supports an optional photo upload; `check_ins.photo_url` populates.
- [ ] `database.types.ts` regenerated and committed.

**Risks & Mitigations:**
- *Client-side direct uploads bypass backend validation* → enforce `fileSizeLimit`/
  `allowedMimeTypes` at the Supabase bucket level.
- *Storage RLS path-based checks are easy to get subtly wrong* → add a backend integration
  test attempting a cross-user upload/read and asserting 403.

### Phase 5a — Studio Billing (Stripe Connect)

**Goal:** Let studios charge their own clients for real, replacing the currently-fake
`payments`/`subscription_plans`/`client_subscriptions` tables with Stripe-backed data.

**Unlocks:** Phase 7's revenue analytics (needs real `payments` rows) and Phase 5b (reuses the
Stripe SDK + webhook infrastructure built here).

**Features & Tasks:**
- **Stripe Connect Express onboarding** for studio owners (new
  `backend/src/modules/billing/`). *Rationale:* studios are merchants of record for their own
  clients' subscriptions — Connect Express gives FitStudio Pro onboarding-UI control while
  Stripe handles KYC/compliance.
- **Map `subscription_plans` → Stripe Products/Prices** via new `stripe_price_id`/
  `stripe_product_id` columns. *Rationale:* keeps the existing plan-management UX while making
  prices Stripe-native.
- **Checkout session creation for `client_subscriptions`** — replaces manually-managed rows
  with webhook-driven `status`. *Rationale:* this is the actual "studios can charge clients"
  capability the brief promises but never implemented.
- **Webhook handler** (`POST /api/v1/billing/webhooks/stripe`) writing to `payments` and
  `client_subscriptions.status`. *Rationale:* `payments` currently has zero write path —
  the admin module can only list it.
- **Idempotency via BullMQ** — enqueue a `stripe-webhooks` job with `jobId = stripe_event.id`
  (Redis-backed dedup) after fast signature verification; actual DB writes happen in
  `worker/src/processors/stripe-webhook.processor.ts`, keeping the HTTP response under
  Stripe's 10-second requirement.

**Technical Notes:**
- New module follows the existing pattern: `billing.routes.ts`/`controller`/`service`/
  `schema.ts`. New dependency: `stripe` npm package.
- New migration adds `studios.stripe_account_id`, `subscription_plans.stripe_price_id`,
  `client_subscriptions.stripe_subscription_id`, `payments.stripe_payment_intent_id` —
  additive nullable columns only, must not break the admin module's existing `listPayments`
  (run Phase 1's admin tests as a regression gate).
- **Webhook body-parsing**: the webhook route must use
  `express.raw({ type: 'application/json' })` and be registered/excluded from `app.ts`'s
  global `express.json()` *before* it — Stripe signature verification needs the raw body.
- **Connect type: Express** (not Standard) — gives FitStudio Pro onboarding-UI control while
  Stripe handles KYC/compliance, appropriate for studio owners who aren't Stripe power users.

**Definition of Done:**
- [ ] Studio owner completes Stripe Express onboarding from `/dashboard/settings`;
      `studios.stripe_account_id` populated.
- [ ] Creating a `subscription_plans` row creates a corresponding Stripe Price on the Connect
      account.
- [ ] Test client completes Checkout (test mode); `client_subscriptions.status` flips to
      `active` via webhook.
- [ ] `payments` rows are created idempotently from `invoice.paid`/
      `checkout.session.completed` (a replayed event produces exactly one row).
- [ ] Invalid webhook signature → 400.

**Risks & Mitigations:**
- *Connect onboarding (KYC) has real-world latency hard to fully test in dev* → build against
  Stripe test mode/Connect test accounts; document a manual production-onboarding checklist
  for Phase 10.
- *Raw-body vs. JSON-parser ordering is a frequent class of bug* → integration test using the
  Stripe CLI (`stripe trigger`) or a hand-signed payload fixture.
- *This is the largest single scope addition in the plan and the one most likely to slip* → if
  it does, Phases 6/7/8 do not hard-depend on it shipping first (Phase 7's revenue endpoints
  simply return zeros until real `payments` exist; Phase 8's "pick a plan" step is skippable).

### Phase 5b — Platform Billing & Plan Gating

**Goal:** Give FitStudio Pro itself a revenue model — studios pay FitStudio Pro, not just
their own clients.

**Unlocks:** Phase 8's pricing page and onboarding "pick a plan" step; this phase IS the
"sellable SaaS" unlock the whole roadmap is framed around.

**Features & Tasks:**
- **New `platform_subscriptions` table** (`studio_id`, `plan_tier`, `stripe_subscription_id`,
  `status`, `started_at`, `ends_at`). *Rationale:* distinct from `subscription_plans` (which is
  studio→client) — this is FitStudio Pro→studio, the actual platform revenue model.
- **Direct (non-Connect) Stripe billing** for studio owners on FitStudio Pro's own account.
  *Rationale:* simplest possible implementation — no KYC/onboarding needed for FitStudio Pro's
  own Stripe account.
- **Feature-gating middleware** (`backend/src/middleware/planGate.middleware.ts`) — e.g. caps
  on trainers/clients per tier, gates Phase 6's group scheduling or Phase 7's advanced
  analytics behind higher tiers. *Rationale:* without gating, "plans" are meaningless —
  this is what makes the tiers actually monetizable.
- **Billing/plan management page** in studio settings (current plan, usage vs. limits, upgrade
  CTA).

**Technical Notes:**
- Reuses Phase 5a's Stripe SDK install and `stripe-webhooks` queue/idempotency pattern —
  dispatch on whether `event.account` is present (Connect events have it, platform events
  don't). Likely two webhook endpoint URLs/secrets (`/webhooks/stripe/connect`,
  `/webhooks/stripe/platform`), both feeding the same queue with a `source` field.
- Plan tiers defined statically in `backend/src/config/plans.ts`
  (`{ free: {...}, pro: {...}, studio: {...} }`) — not a DB table for v1; tiers change rarely,
  code-defined is simpler to version and review.
- `planGate.middleware.ts` looks up `platform_subscriptions.plan_tier` (defaults to `free` if
  no row exists), checks against `plans.ts`, returns `403 { upgradeRequired: true }`.

**Definition of Done:**
- [ ] Studio owner subscribes to a FitStudio Pro plan tier via Checkout (platform account,
      separate from any Connect account).
- [ ] `platform_subscriptions.status` updates via webhook (reusing 5a's processor).
- [ ] `planGate.middleware.ts` blocks an over-limit action (e.g. adding a 2nd trainer on
      `free`) with `403 { upgradeRequired: true }`.
- [ ] Settings page shows current plan, usage vs. limits, and an upgrade CTA.
- [ ] Studios with no `platform_subscriptions` row (existing/seed studios) continue to
      function on the `free` tier — gating is additive, never breaks existing access.

**Risks & Mitigations:**
- *Missing `platform_subscriptions` rows for existing/seed studios could break gating* →
  default absence to `free` (lowest tier, never "unlimited").
- *Two Stripe "modes" (Connect vs. direct) risk config confusion* → explicit env var naming
  and a test asserting Connect calls always pass
  `{ stripeAccount: studio.stripe_account_id }`.
- *Code-defined tiers require a deploy to change pricing* → acceptable for v1; explicitly
  deferred: a DB-driven plan-config admin UI.

### Phase 6 — Scheduling Expansion

**Goal:** Move beyond 1:1 sessions to group/class scheduling — the core value prop of
Mindbody/Glofox/TeamUp.

**Unlocks:** Phase 7's attendance analytics across both session types; Phase 9's calendar UI
work has real data to render.

**Features & Tasks:**
- **Trainer-availability module** (`backend/src/modules/availability/`). *Rationale:* the
  `trainer_availability` table and its RLS policies already exist with zero backend
  consumers — this is the cheapest net-new feature in the roadmap.
- **New `class_sessions`** (studio_id, trainer_id, title, start_time, end_time, capacity) and
  **`class_bookings`** (class_session_id, client_id, status: `booked`/`waitlisted`/
  `cancelled`) tables. *Rationale:* the current `sessions` table is strictly 1:1 with no
  `capacity` column — group classes need new schema, not an extension of the existing one.
- **Capacity + waitlist logic** — extends the conflict-checking pattern from
  `sessions.service.ts` but for capacity instead of time-overlap.
- **Client self-booking within trainer availability.** *Rationale:* Phase 2's portal currently
  only *displays* sessions; this turns it into a real self-service tool.
- **Calendar (week-grid) view** for both `sessions` and `class_sessions`, in both trainer
  dashboard and client portal.

**Technical Notes:**
- `trainer_availability` needs no schema change — just `availability.routes.ts`/`controller`/
  `service`/`schema.ts` mounted at `/api/v1/studios/:studioId/trainer-availability`
  (`mergeParams`, mirroring `clients.routes.ts`).
- New migration for `class_sessions`/`class_bookings` following existing conventions (uuid PK,
  cascading `studio_id` FK, status check constraints, RLS via `is_studio_member`/
  `is_studio_staff`). Partial unique index on
  `(class_session_id, client_id) WHERE status != 'cancelled'` prevents duplicate active
  bookings.
- Capacity/waitlist: `bookClass()` counts `status='booked'` rows; if `< capacity`, insert
  `booked`, else `waitlisted`. **Waitlist promotion needs a Postgres RPC function**
  (`supabaseAdmin.rpc('promote_class_waitlist', { class_session_id })`) using
  `SELECT ... FOR UPDATE SKIP LOCKED` — an application-level read-then-write would have race
  conditions.
- Calendar: build a custom Tailwind week-grid first (avoid `react-big-calendar`/
  `fullcalendar` — large, fights the existing design system); only add a calendar library if
  the custom grid proves too complex, flagged explicitly as a new dependency if so.
- New aggregation endpoint `GET /api/v1/studios/:studioId/calendar?from=&to=` merges
  `sessions` + `class_sessions` server-side into a common
  `{ id, type, title, start, end, ... }` shape.

**Definition of Done:**
- [ ] Trainer-availability CRUD works with owner/self-trainer authorization.
- [ ] `capacity: 2` + 3 bookings → 2 `booked` + 1 `waitlisted`; cancelling a `booked` row
      promotes the waitlisted one via the RPC.
- [ ] Client portal shows available classes filtered by trainer availability, supports
      book/cancel/waitlist.
- [ ] Calendar view renders both session types in a unified week grid.
- [ ] `database.types.ts` regenerated for the new tables.

**Risks & Mitigations:**
- *Waitlist promotion race conditions* → `FOR UPDATE SKIP LOCKED` Postgres RPC, not
  application-level read-then-write.
- *This is the largest net-new schema addition since the original 20-table brief, risking
  >6 weeks* → scope the calendar to week-view-only for v1; defer month view/drag-to-reschedule
  to Phase 9.

### Phase 7 — Advanced Analytics & Reporting

**Goal:** Give studio owners the business intelligence a paid product needs.

**Unlocks:** Phase 8's pricing/marketing claims ("track your revenue and retention") have real
features behind them.

**Features & Tasks:**
- **Revenue trends** (MRR, churn, by-plan) from `payments`/`client_subscriptions`. *Rationale:*
  only meaningful once Phase 5a produces real `payments` rows — this phase is the payoff for
  5a's investment.
- **Client retention (cohort-based)** from `client_subscriptions` — headline metric for
  subscription businesses.
- **Workout adherence** (planned vs. completed `workout_logs`) — existing data, no new schema.
- **Session/class attendance** from `sessions.status`/`class_bookings.status` — extends the
  existing `analytics/overview` owner/trainer scoping pattern.
- **Trainer performance overview** (sessions completed, retention by trainer, attributable
  revenue) — owner-only visibility.
- **CSV export** for all of the above.

**Technical Notes:**
- New endpoints under the existing `backend/src/modules/analytics/` (`/revenue`, `/retention`,
  `/adherence`, `/attendance`, `/trainer-performance`), following the owner/trainer scoping
  pattern already in `getStudioOverviewController`.
- **Caching**: new `backend/src/lib/cache.ts` (`getOrSetCache(key, ttlSeconds, fn)`) wrapping
  the existing `getRedisClient()` singleton — first non-BullMQ use of Redis, using a `cache:`
  key prefix (BullMQ uses `bull:`, no collision). TTL 5–15 min for these aggregations only;
  never cache notifications, booking conflicts, or payments (need real-time correctness).
- CSV export: small `toCsv(rows)` util in `backend/src/utils/`, no new dependency
  (`Content-Type: text/csv` + `Content-Disposition: attachment`).
- Cohort retention queries are likely too complex for the Supabase client's relational
  `select` — use a Postgres view or `supabaseAdmin.rpc(...)` (first DB-side-aggregation
  pattern in this codebase; document it explicitly for future modules).

**Definition of Done:**
- [ ] `/api/v1/studios/:studioId/analytics/revenue` returns MRR + trend, correctly scoped.
- [ ] `/retention` returns cohort retention percentages.
- [ ] Adherence/attendance/trainer-performance endpoints exist with scoping tests mirroring
      `analytics.service.test.ts`.
- [ ] Cache hit verified (mocked `supabaseAdmin` call count doesn't increase within TTL).
- [ ] CSV export works for at least revenue and attendance.

**Risks & Mitigations:**
- *Stale cache could mislead an owner right after a payment/booking* → short TTLs + an
  explicit "Refresh" button.
- *Complex cohort SQL via the Supabase client* → Postgres views/RPC functions, keep the
  service layer thin.
- *Trainer-performance metrics could feel like surveillance* → owner-only visibility, enforced
  in the service layer.

**Unlocks:** this is the front door — without it, "sellable" has no entry point.

**Features & Tasks:**

  defer testimonials/blog/SEO.

  ~7-day expiry, rate-limited via Phase 1's `express-rate-limit`.

## Cross-Phase Architecture Decisions

- **Multi-tenancy model**: keep the existing studio-scoped tenancy (RLS + `studio_id` foreign
  keys via the 15 security-definer helper functions). No schema-per-tenant migration —
  appropriate for the projected scale (small/medium studios, hundreds of tenants).
- **Shared-types strategy**: TS path mapping (`@shared/database` →
  `backend/src/types/database.types.ts`), `import type` only, regenerated via
  `supabase gen types typescript` (already a workspace devDependency) as a documented step in
  any migration PR from Phase 4 onward.
- **API versioning**: all routes wrapped under `v1Router` mounted at `/api/v1` (canonical) with
  `/api` as a temporary alias removed once the frontend migrates. `/api/v2` reserved for
  genuinely breaking changes only; all new Phase 2–9 endpoints go straight into `v1Router`.
- **Background job system**: BullMQ + Redis remains the single job system, gaining new queues
  over time (`emails`, `weekly-summaries` in Phase 3; `stripe-webhooks` in Phase 5a, reused by
  5b). Idempotency for webhook-style jobs uses `jobId = <external event id>` (Redis-backed
  dedup), not a separate "processed events" table.
- **Caching layer**: Redis (already present for BullMQ) gains a second use in Phase 7 — a
  `cache:`-prefixed key namespace for 5–15 min TTL analytics aggregations only. Never used for
  notifications, booking conflicts, or payments.
- **Stripe architecture**: one `stripe` SDK install, two integrations — Phase 5a (Connect
  Express, `studios.stripe_account_id`, all calls pass `{ stripeAccount: ... }`) and Phase 5b
  (FitStudio Pro's direct account, no `stripeAccount` param) — sharing the `stripe-webhooks`
  queue with a `source` field to distinguish event origin.
- **Data schema versioning**: continue Supabase SQL migrations, one feature per migration file,
  never edit applied migrations (the Sprint 0 cleanup of the redundant
  `20260525101235_add_email_to_profiles.sql` establishes this convention going forward).
- **Auth/email-confirmation strategy for production**: once Phase 3 ships Resend, switch
  Phase 2's auto-created client accounts from
  `createUser({ email_confirm: true, password: 'fitstudio@123@' })` to
  `inviteUserByEmail()` so clients set their own password — exactly as flagged in
  `futureModifications.md` item 2. Configure production Supabase SMTP to relay through Resend.
  Password resets continue via Supabase's built-in `resetPasswordForEmail()`, with production
  Site URL/Redirect URLs configured (the production analog of the local fix in
  `memory/project_forgot_password_fix.md`).

## Deferred / Out-of-Scope Items

- **Multi-branch gym management** — `studios` is single-location; multi-branch needs a new
  `locations` table touching nearly every RLS policy and module. Too large until the
  single-location product is validated.
- **Native mobile (Flutter) app** — Phases 1 and 10 already produce a versioned, documented
  `/api/v1` a future app could consume. The app itself is a separate product surface/team, not
  needed for the web SaaS to be sellable.
- **Trainer-client messaging/chat** — needs WebSocket/SSE infra absent from the stack
  (Phase 2's notifications are poll-based). Justify real-time infra only after Phases 5–6
  validate the business model.
- **Wearable integrations** (Apple Health, Whoop, etc.) — each is its own OAuth/API
  maintenance burden; existing check-ins/measurements already cover "track progress" without
  external dependencies.
- **Nutrition plans** — comparable in size to the existing `workouts` module; Mindbody/Glofox
  treat it as a separate tier. Defer until core scheduling/billing/portal is complete.
- **Video workout content** — `exercises` has no video field; needs a CDN/transcoding strategy
  beyond Phase 4's image buckets. Revisit only after Phase 4 proves the storage/RLS pattern.
- **Third-party calendar sync** (Google Calendar etc.) — Phase 6 establishes the internal
  scheduling model first; OAuth-heavy two-way sync is best tackled once `sessions`/
  `class_sessions` is stable and unlikely to need schema changes that complicate a sync
  mapping.
